# 协议 5.5 事件数据对应关系与代码处理

本文专门解释协议 5.5.1“故障数据”和 5.5.2“报警数据”为什么在 `Int=0` 下列出了很多不同含义，以及 WireLink 如何根据事件类型选择正确的解释方式。

## 1. 最容易误解的地方：`Int=0` 不是“值为 0”

5.5.1 表格第一列写的：

```text
Int
0
1
2
3
4
5
6
7
```

这里的 `Int` 实际表示**事件附加数据的序号**，可以直接理解成：

```text
Int=0 → 事件数据0
Int=1 → 事件数据1
Int=2 → 事件数据2
...
Int=7 → 事件数据7
```

它不是：

- 事件数据的原始值等于 0；
- 故障类型码等于 0；
- 没有故障；
- 寄存器地址 0。

协议表把 `Int=0` 的单元格纵向合并了，所以视觉上会看到一个“0”对应很多行。实际意思是：

> 事件数据 0 只有一个，但它的业务含义由“事件类型”决定。

例如，完全相同的原始数值 `125`：

```text
如果事件类型是过载故障：
    数据0表示故障电流

如果事件类型是电流不平衡故障：
    数据0表示最大电流不平衡率

如果事件类型是欠压故障：
    数据0表示故障线电压

如果事件类型是欠频故障：
    数据0表示故障频率
```

所以不能只拿到“数据 0”就直接换算。必须先知道这是哪一种故障或报警。

### 1.1 协议中几种“0”的完整区别

协议中的数字没有脱离字段而独立存在。必须先确定这个 `0` 位于哪个寄存器、哪个字节或哪一列，再解释它的含义。

先把寄存器 785 按协议原文拆开：

```text
785：L：指定要读取的记录类型(char) H：指定要读取第几条记录(char)

一个 16 位寄存器：

        高字节 H                 低字节 L
┌────────────────────┬────────────────────┐
│ 第几条记录 0～15    │ 记录类型 0～2       │
│ bit8～bit15        │ bit0～bit7         │
└────────────────────┴────────────────────┘

组合公式：
785的值 = (第几条记录 << 8) | 记录类型
```

所以你说的完全对：**785 的高位 H 是“指定要读取第几条记录”，低位 L 才是“指定要读取的记录类型”。**

| `0` 出现的位置 | 它表示什么 | 它不表示什么 |
|---|---|---|
| 785 的 L/低 8 位值为 0 | 选择记录类型 0：故障跳闸记录 | 不是无故障 |
| 785 的 H/高 8 位值为 0 | 指定要读取第 0 条记录，也就是最近的一条数据 | 不是固定记录 ID |
| 785 整个寄存器为 `0000H` | 故障跳闸记录、最近的一条 | 不是把故障记录清零 |
| 5.5.1 第一列 `Int=0` | 选择“事件数据 0”这个字段 | 不是数据内容等于 0 |
| 515/771 高 8 位的值为 0 | 具体事件类型码为 0：故障表中是“无故障”，报警表中是“无报警” | 不是第 0 条记录 |
| 515/771 低 8 位的值为 0 | 一般表示 A 相；当故障类型为 18 时表示 DI1 | 不是故障类型 0 |
| 516/772 中保存的原始数值为 0 | “数据 0”的实际原始内容为 0，仍要按事件类型换算 | 不一定表示无事件 |
| 相序事件的数据 0 为 0 | 不是协议规定的 1=ABC、2=ACB，代码会标记未知相序 | 不是 A 相 |

例如同时出现下面这些值：

```text
785 = 0000H
771 = 0700H
772 = 0000H
```

要逐个按位置解释：

```text
785的L/低8位 = 00H → 记录类型是“故障”
785的H/高8位 = 00H → 指定要读取第0条记录，也就是最近的一条数据

771高8位     = 07H → 具体事件类型是“过载故障”
771低8位     = 00H → A相

772          = 0000H → 事件数据0的原始内容是0
                         因类型7是电流类，结果为 0 × 电流变比 = 0 A
```

再举一个不全是 0 的例子：

```text
要读取“报警第 3 条记录”：

第几条记录 = 3 → 放进 785 的 H/高8位 → 03H
记录类型   = 1 → 放进 785 的 L/低8位 → 01H

785 = 0301H
```

如果用 06H 写这个寄存器，报文中的数据值会写成 `03 01`。这里 `03` 是高字节 H，也就是“第几条记录”；`01` 是低字节 L，也就是记录类型。

这里至少有四种不同作用的“0”。判断顺序始终是：

```text
先看位置/字段
    ↓
再确定这个字段的编码表
    ↓
最后解释该字段中的0
```

## 2. 这是“带类型的数据结构”

可以把协议结构理解成：

```text
事件记录
├─ 事件大类：故障 / 报警 / 变位
├─ 事件类型：过载、欠压、漏电、相序……
├─ 事件相别：A、B、C、N……
└─ 附加数据：
   ├─ 数据0
   ├─ 数据1
   ├─ 数据2
   ├─ 数据3
   ├─ 数据4
   ├─ 数据5
   ├─ 数据6
   └─ 数据7
```

“附加数据”的含义不是固定的，而是由前面的事件类型决定。这种结构在程序设计里通常称为：

```text
带类型的联合数据
Tagged Union
Discriminated Union
```

最直接的理解是：

```text
先看标签是什么，
再按该标签解释后面的数据。
```

类似一个表单：

```text
类型=温度 → 数值按摄氏度解释
类型=频率 → 数值按Hz解释
类型=电流 → 数值按A解释
```

虽然原始寄存器都是同一个 `uint16`，业务含义可以完全不同。

## 4. 如何取得“事件大类”

事件大类决定使用：

- 5.5.1 故障数据；
- 5.5.2 报警数据；
- 或项目暂定的变位原值处理。

### 4.1 当前事件

当前事件由寄存器 512 判断：

```text
512.bit3 = 1 → 故障
512.bit2 = 1 → 报警
bit3和bit2同时为1 → 故障优先
bit3和bit2都为0 → 当前没有故障或报警
```

伪代码：

```text
if 512.bit3 == 1:
    事件大类 = 故障
else if 512.bit2 == 1:
    事件大类 = 报警
else:
    当前没有故障或报警
```

### 4.2 历史事件

历史事件的大类来自界面选择：

```text
故障 = 0
报警 = 1
变位 = 2
```

程序先把：

```text
selector = (第几条记录 << 8) | 事件大类
```

通过 06H 写入寄存器 785，然后读取历史记录区 768～785，并单独读取 1552 的额定电流配置。

历史数据解析时，界面选择的大类会直接传给解析器：

```text
选“故障” → 按故障类型表和 5.5.1 解释
选“报警” → 按报警类型表和 5.5.2 解释
选“变位” → 暂按原值解释
```

## 5. 如何取得“具体事件类型”

当前地址 515、历史地址 771 的结构相同：

```text
高 8 位：具体事件类型
低 8 位：事件相别
```

计算公式：

```text
事件类型码 = register >> 8
相别码     = register & 00FFH
```

例如：

```text
771 = 0700H

事件类型码 = 07H
相别码     = 00H
```

如果大类是故障：

```text
故障类型码 7 = 过载故障
相别码 0 = A相
```

最终解释：

```text
A相 / 过载故障
```

再根据“过载故障”去解释数据 0～7。

## 6. 完整判别流程

```text
取得当前或历史原始寄存器
    ↓
判断事件大类
    ├─ 当前：检查512.bit3/bit2
    └─ 历史：使用界面选择的故障/报警/变位
    ↓
读取515或771
    ↓
高8位得到具体事件类型码
低8位得到相别码
    ↓
读取数据0～7
    ↓
根据“事件大类 + 具体类型码 + 数据序号”
选择对应的单位、倍率和含义
```

程序中的核心逻辑可以简化成：

```text
if 大类 == 故障:
    按故障类型码解释数据0

if 大类 == 报警:
    按报警类型码解释数据0

if 大类 == 变位:
    暂时显示原始值
```

## 8. 用三个例子理解“同一个数据 0”

### 8.1 过载故障

原始寄存器：

```text
771 = 0700H
772 = 007DH
1552 = 030BH
控制器 = BW1
```

第一步，解析 771：

```text
高8位 = 07H → 过载故障
低8位 = 00H → A相
```

第二步，解析数据 0：

```text
772 = 007DH = 十进制125
1552 & 00FFH = 000BH → 十进制序值11
高位 03H 是框架等级/保留信息，不参与额定电流序值计算
BW1序值11 → 电流变比2
125 × 2 = 250 A
```

结果：

```text
A相 / 过载故障
故障数据0 = 250 A
```

### 8.2 电流不平衡故障

```text
771 = 0F04H
772 = 0023H
```

解释：

```text
高8位 0FH = 类型15 = 电流不平衡故障
低8位 04H = 无特定相别
数据0原值 0023H = 十进制35
```

类型 15 规定数据 0 是最大电流不平衡率：

```text
结果 = 35%
```

### 8.3 欠频故障

```text
771 = 0204H
772 = 1386H
```

解释：

```text
高8位 02H = 类型2 = 欠频故障
数据0原值 1386H = 十进制4998
```

类型 2 规定数据 0 是频率，倍率 `×0.01`：

```text
4998 × 0.01 = 49.98 Hz
```

这三个例子都读取“数据 0”，但由于类型码不同，分别得到：

```text
250 A
35%
49.98 Hz
```

| 0 | 无报警 |

| 16 | 通讯链接失败报警 |
| 17 | 自诊断报警 |
| 18 | 触头磨损报警 |
| 19～20 | 保留 |

协议 5.4.2 规定报警类型码范围为 `0～21`。如果设备返回 22 或更大的类型码，协议没有对应中文名称，数据 0 同样直接显示十进制原值。

COM5 实机选择“报警 / 第 0 条记录”后返回：

```text
771 = 1601H → B 相，报警类型码 22（协议未定义）
772 = 00C8H → 十进制 200
```

因此界面的“故障数据 0”显示 `200`，不把它猜成电流、温度或其他工程量。

## 10. 故障数据 1～7 在协议中的含义

### 10.1 数据 1 和数据 2

5.5.1 规定：

```text
数据1 = 延时时间低字
数据2 = 延时时间高字
完整延时时间 = 组合值 / 50 秒
```

按协议文字推导，组合方式应为：

```text
计数值 = (数据2 << 16) | 数据1
延时时间 = 计数值 / 50 秒
```

示例：

```text
数据1 = 0064H
数据2 = 0000H

计数值 = 100
延时时间 = 100 / 50 = 2 秒
```

当前代码尚未组合这两个寄存器，也没有除以 50，而是分别显示十进制原值。

### 10.2 数据 3

协议规定：

```text
数据3 = 故障设定动作值
```

不同故障应关联不同保护设定：

```text
过载故障 → 过载保护动作值
欠压故障 → 欠压保护动作值
短路故障 → 短路保护动作值
MCR/HSISC → 单位kA
```

但原协议没有在 5.5.1 中给出完整的一一对应地址和倍率。

当前代码直接显示十进制原值，不添加单位：

```text
原值1234 → 显示1234
```

### 10.3 数据 4～7

对于过载、短路、接地、漏电、电流不平衡、最大需用、逆功率、DI 跳闸、区域连锁及相应试验故障：

| 数据序号 | 含义 | 协议换算 |
|---:|---|---|
| 4 | A 相电流 | ×电流变比 |
| 5 | B 相电流 | ×电流变比 |
| 6 | C 相电流 | ×电流变比 |
| 7 | N 相电流 | ×电流变比 |

对于相序、欠频、过频、欠压、过压、电压不平衡等电压类事件：

| 数据序号 | 含义 | 协议换算 |
|---:|---|---|
| 4 | Uab | ×1 V |
| 5 | Ubc | ×1 V |
| 6 | Uca | ×1 V |

协议还规定部分电压类故障的数据 7 是系统频率：

| 数据序号 | 适用类型 | 含义 | 换算 |
|---:|---|---|---|
| 7 | 相序、欠压、过压、电压不平衡 | 系统频率 | ×0.01 Hz |

当前代码尚未实现这些按类型换算，数据 4～7 只显示十进制原值。

## 11. 报警数据 1～7 为什么为空

5.5.2 只列出了一组 `Int=516`，没有继续列出 517～523，也没有说明报警数据 1～7。

WireLink 当前按以下规则处理：

```text
报警只有数据0有效
当前报警517～523留空
历史报警773～779留空
```

返回状态仍是成功，不显示协议警告：

```text
值 = 空字符串
公式 = 报警仅数据0有效，本字段为空
状态 = Success
```

这是项目对协议表的解释，不是原始协议十分明确的文字说明。如果实机证明报警数据 1～7 有内容，需要补充协议规则后修改。

## 12. 变位记录如何处理

协议 5.7 允许选择类型 2“变位记录”，但没有给出独立的变位数据结构。

当前项目：

```text
771 → 仍按低8位相别、高8位类型显示
772 → 显示无符号十进制原值
773～779 → 显示十进制原值
```

不会把变位数据强行解释成故障电流、频率或报警值。

## 13. 当前没有故障或报警时

如果当前寄存器 512：

```text

bit2 = 0
```

程序认为当前没有故障或报警：

```text
515显示：无当前故障/报警

```

这是正常状态，不生成警告。

## 16. 最短理解方式

看到 5.5.1 的表格时，按下面顺序阅读：

```text
第一步：Int 是数据序号，不是数据值。

第二步：先从515/771高8位取得事件类型。

第三步：在 Int=0 的多行规则中，
       找到与事件类型匹配的那一行。

第四步：按照该行的含义、单位和倍率解释516/772。

第五步：数据1～7再分别按自己的序号和事件类型解释。
```

一句话总结：

> `Int=0` 代表“数据 0 这个位置”；究竟是电流、百分比、电压、频率、相序还是功率，由 515/771 高 8 位中的事件类型码决定。
